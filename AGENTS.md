# AGENTS

## Purpose

This file provides repository-local instructions for coding agents working in `marisco`.

Use it together with:

- `C:\dev\marisco3\marisco_clean\marisco_repo\PROJECT.md`
- `C:\dev\marisco3\marisco_clean\marisco_repo\ARCHITECTURE.md`
- `C:\dev\marisco3\marisco_clean\marisco_repo\DEPENDENCIES.md`
- `C:\dev\marisco3\marisco_clean\marisco_repo\CONVENTIONS.md`

## Repo Shape

- `nbs/` contains the implementation source of truth
- `marisco/` contains Python modules generated from notebooks through `nbdev`
- `marisco/cli/` contains public CLI entrypoints
- `marisco/handlers/` contains generated provider `Handler` modules
- `nbs/api/` contains shared notebook sources for callbacks, configs, encoders, decoders, metadata, and utilities
- `nbs/handlers/` contains notebook sources for provider-specific logic
- `nbs/files/` contains static assets such as LUTs, CDL, templates, and sample data

## Source Of Truth

- Treat `nbs/` as the primary implementation surface.
- Treat `marisco/` as generated output unless there is a compelling short-term reason not to.
- If a file says `AUTOGENERATED! DO NOT EDIT!`, do not make that file the only place where behavior changes live.
- Behavior changes, naming changes, CLI UX changes, and error-handling changes should be made in the corresponding notebook first.
- If a generated `.py` file must be patched temporarily, mirror that change back into the matching notebook as soon as possible.

## Editing Rules

- Prefer minimal, targeted changes.
- Do not make broad cleanup edits unrelated to the task.
- Do not reformat or rename widely unless it is required for the requested change.
- Keep notebook-generated and package code aligned.
- Prefer extending shared callbacks or utilities when logic is reusable across `Handler`s.
- Keep provider-specific quirks inside the relevant provider notebook unless they clearly belong in shared code.

## Naming Rules

- Public CLI entry functions should be named `main`.
- Main conversion functions should be named `encode` or `decode`.
- Callback classes should use `PascalCase` with a `CB` suffix.
- Callback names should start with an action verb such as `Add`, `Remap`, `Parse`, `Normalize`, `Convert`, `Extract`, or `Sanitize`.
- Use `df` for a single `DataFrame` and `dfs` for a collection of grouped `DataFrame` objects.
- Use `grp` for internal group keys and `group_name` for descriptive output.
- Use `src` and `dest` for CLI-facing path arguments.
- Use `fname_in`, `fname_out`, and `dir_dest` for internal file and directory arguments.
- Use `*_path()` for path helpers and `*_lut_path()` for LUT path helpers.

## CLI And UX Rules

- This repository is CLI-first. Optimize for clear terminal UX.
- All public CLI commands should preserve `-h/--help` behavior.
- Validate user input before expensive work begins.
- Use non-zero exit status for user-visible CLI failure.
- Print a clear start message before long-running work.
- Show progress for long-running or repeated work.
- Print a clear completion message with output location.
- Do not leave the user guessing whether a command succeeded.

For user-facing failures:

- say what failed
- name the relevant file, URL, handler, group, or lookup when possible
- say whether processing stopped or continued
- tell the user what to check next

Avoid low-information messages such as:

- `Error: 404`
- `Failed`
- `not found`

unless they are expanded with context.

## Progress Expectations

Progress feedback is expected for:

- remote downloads
- repeated file loads
- repeated sheet loads
- repeated `ref_id` exports
- fuzzy matching over many rows
- large NetCDF encode or decode operations
- large CSV export operations

Prefer progress bars for repeated units of work. At minimum, show start, current stage, and completion.

## Runtime Preconditions

Assume the following may be required before runtime code works correctly:

- `maris_init` has been run
- `~/.marisco/` exists
- LUT files are available under `.marisco/lut/`
- `maris-template.nc` exists under `.marisco/`
- `ZOTERO_API_KEY` is available for metadata flows that require Zotero

Be careful when changing code that depends on:

- GitHub downloads
- Zotero
- cache behavior
- NetCDF template contents
- handler-specific remote sources

## Validation

There is no dedicated top-level `tests/` directory in this repository, so validation should be practical and scoped.

Prefer this order:

1. check the smallest affected surface first
2. run lightweight static validation where possible
3. use CLI help commands for entrypoint sanity checks
4. only then move to broader validation if needed

Useful validation commands include:

- `maris_init -h`
- `maris_to_nc -h`
- `maris_db_to_nc -h`
- `maris_nc_to_csv -h`
- `python -m py_compile <touched_python_files>`

If the change affects the NetCDF template workflow, the relevant system-level command is:

- `ncgen -4 -o nbs/files/nc/maris-template.nc nbs/files/cdl/maris.cdl`

## High-Risk Areas

Take extra care around:

- notebook source vs generated code drift
- `.marisco/` initialization assumptions
- cache-dependent handlers such as `OSPAR`
- external network dependencies and download failures
- metadata enrichment flows that depend on Zotero
- template and LUT changes that can affect multiple handlers at once

## Working Heuristics

- Read the matching notebook before making non-trivial changes to generated code.
- If a change touches a `Handler`, also inspect related shared callbacks and config vocabulary.
- If a task changes UX, make sure success, warning, and failure output remain coherent.
- If a task changes runtime assumptions, update the relevant docs.

## When In Doubt

- prefer `nbs/` over `marisco/`
- prefer small diffs over large rewrites
- prefer explicit user-facing messages over silent fallback
- prefer reusable shared logic over duplicated provider-specific logic
