# CONVENTIONS

## Purpose

This document defines the minimum implementation and UX conventions for `marisco`.

The goal is not only code consistency, but also a minimum hospitality bar for users:

- invalid input should not fail silently
- long-running work should not leave users guessing
- successful runs should clearly tell users what was produced
- maintainers should edit the notebook source of truth, not only generated Python

## Scope

These conventions apply to:

- public CLI entrypoints under `marisco/cli/`
- provider `Handler` implementations under `nbs/handlers/`
- shared callback, encoder, decoder, metadata, config, and utility logic under `nbs/api/`
- generated Python modules under `marisco/` as outputs of the notebook workflow

Current enforcement priority is **CLI-first**.

This repository does not currently implement a GUI layer. If a GUI is added later, it must follow the same user-facing principles defined here, but GUI-specific interaction rules should be documented separately.

## Source Of Truth

- `nbs/` is the implementation source of truth.
- `marisco/` contains generated Python modules produced through `nbdev`.
- Files marked `AUTOGENERATED! DO NOT EDIT!` must not be treated as the primary edit target.
- Behavior changes, naming changes, error-handling changes, and UX changes must be made in the corresponding notebook first.
- Direct edits to generated `.py` files are exceptional and temporary. If such an edit is unavoidable, the matching notebook must be updated immediately afterward.

## Naming Conventions

### Public entrypoints

- Public CLI entry functions should be named `main`.
- Main conversion functions should be named `encode` or `decode`.
- Dynamic handler loading should target the public `encode` function of the selected module.

### Classes

- Core classes use `PascalCase`.
- Callback classes use `PascalCase` with the `CB` suffix.
- Callback names should start with an action verb that describes behavior, such as `Add`, `Remap`, `Parse`, `Normalize`, `Convert`, `Extract`, or `Sanitize`.

### Variables and parameters

- Use `df` for a single `DataFrame`.
- Use `dfs` for a dictionary or collection of `DataFrame` objects.
- Use `grp` for internal group keys and `group_name` for user-facing or descriptive group labels.
- Use `src` and `dest` for CLI-facing path arguments.
- Use `fname_in`, `fname_out`, and `dir_dest` for internal file and directory arguments.
- Use `verbose`, `use_cache`, `save_to_cache`, `overwrite`, and `inplace` for boolean behavior flags.

### Columns, paths, and constants

- Use `col_*` or `*_col` for column-name parameters.
- Path helpers should use the `*_path()` form.
- Lookup table path helpers should use the `*_lut_path()` form.
- Shared constants should use `UPPER_SNAKE_CASE`.

## Handler And Callback Design

- A `Handler` is responsible for provider-specific ingestion and normalization.
- Shared logic should be moved into reusable callbacks or utility functions instead of duplicated across handlers.
- Callback pipelines should remain readable and ordered by transformation flow.
- Provider-specific quirks should stay in the provider notebook unless they are clearly reusable elsewhere.

## CLI UX Minimum Bar

All public CLI commands must satisfy the following:

- provide `-h` and `--help`
- validate user input before starting expensive work
- use non-zero exit status for user-visible failure
- print a start message for the requested operation
- print a completion message with output location
- avoid leaving the user uncertain about whether the operation succeeded

For invalid user input:

- explain what is invalid
- show valid choices when the input is from a fixed set
- avoid stack traces unless the failure is unexpected and not recoverable at the CLI boundary

For destructive or overwrite-prone actions:

- require explicit confirmation before replacing existing user-managed files or configuration

## Hospitality Baseline

The system minimum quality bar is:

- do not leave users waiting without feedback
- do not fail with context-free messages
- do not make users guess the next step
- do not overwrite important local state without confirmation

Every user-facing workflow should communicate:

1. what is about to happen
2. what is happening now
3. what succeeded or failed
4. what the user should do next, if anything

## Error Handling

### CLI boundary

- Handle user-facing validation errors in the CLI layer.
- Convert expected user mistakes into clear messages plus a non-zero exit.
- Include the failing input and the valid alternatives when available.

### Internal library code

- Raise exceptions for programmer errors, unsupported states, invalid assumptions, or missing required runtime prerequisites.
- Do not silently swallow internal errors that make results unreliable.

### Warnings

- Use warnings or warning-style messages only for recoverable data-quality issues.
- Typical warning cases include missing optional values, unmatched lookup values, or partial metadata enrichment failures.
- A warning should state the affected item, the impact, and whether processing continues.

### Prohibited failure style

Avoid low-information failures such as:

- `Error: 404`
- `Failed`
- `not found` without naming the missing target and impact

Instead, state:

- what failed
- which file, URL, handler, group, or lookup was involved
- whether the run can continue
- what the user should check next

## Progress And Long-Running Work

Progress feedback is required for operations that may take noticeable time, especially:

- remote downloads
- multiple file loads
- multiple sheet loads
- multiple `ref_id` exports
- fuzzy matching over many rows
- large NetCDF encode or decode operations
- large CSV export operations

Minimum progress behavior:

- announce the start of the operation
- show per-item or per-stage progress for iterative work
- announce completion

Preferred progress behavior:

- use a progress bar for repeated units of work
- show cache usage explicitly
- show which stage is currently running
- show the final output path or paths

## I/O And Path Conventions

- CLI arguments should remain concise and user-oriented.
- Internal function signatures should make file and directory roles explicit.
- Output-writing code should always report where files were saved.
- Cache-aware code should clearly distinguish between loading from cache and fetching fresh remote data.

## Review Checklist

Before considering a change complete, verify:

- the change was made in the correct notebook source when applicable
- public naming follows the existing project patterns
- CLI failures are clear and actionable
- long-running steps provide visible progress
- success messages identify produced outputs
- warnings are recoverable and exceptions are reserved for real failure states

## Future Extension Rule

If this repository later adds a GUI layer, the GUI must preserve the same behavioral promises:

- clear input validation
- explicit confirmation before destructive actions
- visible progress during long-running work
- actionable failure messages
- explicit success summaries

GUI-specific widgets, dialogs, and interaction details should then be documented in a separate UI-focused conventions document rather than weakening this CLI-first baseline.
